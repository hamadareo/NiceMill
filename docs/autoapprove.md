# 自動承認（機械チェックを通った文だけを、人が見ないまま承認する）

作成 2026-11-19。作業ごとのスイッチで使う機能で、既定はオフ。使うかどうかは、運用する人が作業ごとに決める。
検証に使ったのは公開クリップ（Samsunspor, TBF, CC BY 3.0）の処理結果だけで、利用者・参加者の動画・データは使っていない。クラウドAPIは使っていない。
倫理・同意の状況は「現在確認中」。

## 1. これまでの承認の動作（コードで確かめた事実）

- AIが作った文章（人ごとに1つ。`pfb` の最新の実行）は下書き。人が「承認する」を押して初めて、PDFなどに載る（`services.review.approve`、承認した実行の番号を `subjects.approved_run_id` に残す）。文章が新しくなったり解析が更新されると、承認は無効になる（`subject_status`）。
- 人の承認の道は3つ: 一人ずつ「承認する」／「直す」（直して承認）／「全員まとめて承認」（画面に出ていた文章のうち、気になる点が無く根拠が足りているものだけ）。取り消しは「承認を取り消す」（管理用の画面）。「この人だけ作り直す」で文章を作り直せる。
- 自動承認は以前からあった。作業ごとのスイッチ `assignments.auto_approve`（既定 0 = オフ）。オンのときだけ、ワーカーが新しい文章の完成後に `review.auto_approve` を呼ぶ。以前の条件は「承認の関門」だけ（`review._skip_reason`: 新しい・生成済み・文章の警告なし・人物の確定済み・短い文でない・評価対象）。人物の取り違え、動作の断定、比較表現、背番号の書き方、根拠の数は見ていなかった。承認した印は `subjects.approved_auto = 1` と監査記録 `auto_approved` だけで、どのチェックを通ったかの記録は無かった。PDFには「自動で作り、そのまま渡しています」と書いていた。
- 言い換え（やさしい文章版）は機械チェックのみ（`pipeline.plain_checks`）。この機能とは別。
- 承認した文だけが渡る（PDF・共有ページ・成長の記録）。この点は変わらない。

## 2. この機能が変えたこと

1. 自動承認の条件を、上の「承認の関門」だけから、**機械チェック10項目をすべて通ったときだけ**に厳しくした（`services/autoapprove.py`）。スイッチは同じもの（作業ごと、既定オフ）。名前を「機械チェックを通った文を自動承認する」にした。
2. 自動承認は「**自動承認（機械チェック済み・人は未確認**）」として、人の承認と見た目も記録も別にした。花丸の印は人の承認だけ。承認数の表示も「承認 n / 全 m」は人の分だけで、自動承認は「＋ 自動承認 k（人は未確認）」と別に出す。
3. 自動承認ごとに、通ったチェックの一覧・日時・設定の版をDBに残し、一覧で見られ、まとめて取り消せる。
4. 自動承認では、練習のヒント（次にためしてみること）を確定しない。人の承認だけがヒントを確定する（以前は自動承認でも確定していた）。
5. 渡す資料の文言を変えた（下の6）。

## 3. チェック一覧（すべて通ったときだけ自動承認）

文章は人ごとに1つなので、判定の単位はその人の文章（根拠の場面を含む）。動画の作業だけが対象。文書の作業は常に人が確認する。

| ID | 見ること | 使った既存の仕組み | 通らないときの理由（画面に出す文） |
|---|---|---|---|
| base | 承認できる状態（新しい・生成済み・警告なし・人物が確定済み・短い文でない・評価対象）。人が取り消した文でない | `review._skip_reason` | 状態に応じた既存の理由 ／「自動承認が取り消されたため、人が確認します」 |
| evidence | 根拠の場面が実在し、よかった場面と判定され、この人自身の記録である | `checks.evidence_ref_errors`、貢献の判定、行動の記録の参加者 | 場面が見つからない／よかった場面として記録されていない／別の人の記録が混ざっている |
| scenes | 根拠が `auto_approve_min_scenes`（既定2）場面以上 | プロンプトの「2〜3場面」に合わせた | 「根拠の場面がN件で、必要な2件に足りません」 |
| confidence | 根拠の全場面の確信度が `auto_approve_min_confidence`（既定 high）以上 | 行動の記録の `confidence` | 確信度の低い場面が含まれる |
| identity | 根拠の全場面で、その時刻の背番号の読み取りが本人の番号と一致（同じ人）。別の番号を読んだ（別人かも）／近くで何も読めない（判定不能）が1場面でもあれば止める。同じ人に違う番号、同じ番号が他の人にもある場合も止める | `pipeline.identity_check`（背番号の時系列） | 別の人かもしれない場面／同じ人か判定できない場面／ちがう背番号／同じ背番号の人がほかにもいる |
| claims | 文が述べる動作（シュート・ドリブル・パス・守り・走る）が、`claim_check` の再確認で「確認できた」（supported・断定のまま）と記録されている。弱めた場面（hedge/fallback）を含む文、「要確認」「ように見える」を含む文は自動承認しない | `pipeline.claim_check`、`review_video.claims.sentence_actions` | 動作を弱めた場面がある／弱めた言い方が文にある／動作の断定が映像の再確認で確かめられていない |
| wording | 比較・順位づけ・評価の言葉が無い | `review_video.claims._COMPARE`、`services.ask` の評価語・順位の語 | 比較・順位づけ・評価の言葉があります（語を示す） |
| jersey | 背番号は「N番？」の形（「N番」「#N」「背番号」は止める） | 背番号の扱いの決まり | 背番号が「N番？」の形ではない |
| player | 審判・コート外（選手以外）の疑いが無い | 名前の段階のチーム判定（どちらのチームでもない）、参加の判定（要確認・参加していない） | 選手以外かもしれません |
| text | 空でも極端に短く（`auto_approve_min_chars`、既定20字未満）もなく、同じ文のくり返しも、他の人と同じ文も無い | `checks.normalize_text` | 文が短すぎる／同じ文がくり返し／ほかの人と同じ文 |

新しく作ったチェックは、wording の語彙の合成、jersey の正規表現、text の長さと重複、player の判定の組み合わせだけ。

注意（claims の現状）: 再確認の結果を行動の記録の `claim_checks`（場面ID→`claim_check.Verdict` の辞書）から読む。現在のパイプラインはこれを書かない（再確認は `review_video` の画面用だけ）。そのため、動作の言葉を含む文章は、再確認を組み込むまで、すべて「人の確認待ち」になる。

## 4. 設定

- 作業ごとのスイッチ `assignments.auto_approve`。**既定はオフ**。「確認して承認」の画面と管理用の画面（確認・承認）にあり、説明は画面に出る（何を自動で通し、何を人に回すか）。オフのときは従来どおり（自動承認の表示も出ない）。
- 厳しさ（`Settings`）: `auto_approve_min_scenes`（2）、`auto_approve_min_confidence`（high）、`auto_approve_min_chars`（20）。設定の版は `auto-approve/1`（記録に値も残す）。
- スイッチを入れたあと、すでに待っている文章には自動では効かない（これから作られる文章に効く）。「いま待っている文章にも機械チェックをかける」を押すと、待っている文章に同じチェックをかける。

## 5. 記録・一覧・取り消し

- 追加のテーブル `auto_approvals`（subject, run, 日時, 設定の版, 設定の値, 全チェックの結果、状態 active / revoked / confirmed / replaced）。既存の表・列は変えていない（追加のみ。既存DBに新しい表を足すときは、これまでと同じく先にDBのコピーを作る）。
- 移行: `init_schema`（`storage/db.py`）は `auto_approvals` の表を足すだけで、既存の表・行は変えない。何度実行しても同じ。既存のDBに表を足す前に、`app.db.pre-migrate-<時刻>` のコピーを作る。
- 「自動承認した文章の記録」（画面の折りたたみ）に、人・日時・設定の版・通ったチェック・文章を出す。
- 「自動承認を取り消して人の確認待ちに戻す」: 作業の自動承認を一括で取り消す。人が承認したものは変えない。一人だけ取り消す「この人の自動承認を取り消す」、人が確認して承認し直す「人が確認して承認する」もある（その場合は状態 confirmed）。取り消した文章は、同じ文章のままでは二度と自動承認しない。
- 監査記録: `auto_approved`（承認時）、`auto_approval_revoked`（取り消し）。

## 6. 画面と渡す資料

- 承認の画面: 「自動承認 N件／人の確認待ち M件」、自動承認の文章には「自動承認（機械チェック済み・人は未確認）」の印（花丸ではなく破線の印）、人の確認待ちの文章には止めた理由、「人の確認待ちだけを見る」フィルタ。
- 渡す資料（PDF・共有ページ）: 自動承認の人の分には「このフィードバックは動画をもとに自動で作りました。機械チェックは通りましたが、（評価する人は）確かめていません（機械チェック済み・人は未確認）。」と書く。評価する人用の表紙にも、人数を分けて書く。この文言は設定で消せない。

## 7. 限界と注意

- **機械チェックは文章の正しさを保証しない**。人の確認の代わりではなく、確認の手間を減らす仕組み。
- identity は、名前の段階の背番号の読み取りに頼る。この読み取りは精度の関門（保持データで 6/7、n=7 < 20）を越えておらず、公式にはオフ。読み取れていない人は「判定不能」で止まる。読み取りが同じ番号を間違えて読んでも、このチェックでは見分けられない。
- claims は、再確認が組み込まれるまで、動作の言葉を含む文章を通さない。再確認自体も採点25件での確認で、正しい文を弱めすぎる／弱めない誤りの率は十分に測れていない（`docs/claims_20261118/IMPROVE.md`）。
- 時間の言葉（「動画の約2分ごろ」）と根拠の場面の時刻の一致、文中の「チームに貢献」などの評価的な言い回しの意味は見ていない。
- 選手以外の判定は、映像の色を使う `review_video.nonplayer` は使っていない（映像を開かないため）。名前の段階のチーム判定と参加の判定だけ。
- 自動承認後に、人の目で誤りが見つかる可能性は残る。評価する人はいつでも直せる・取り消せる。

## 11. 動作の再確認のパイプライン組み込み（2026-11-19 追加）

### 11.1 何を組み込んだか

文章（pfb の run）ができた直後、その作業の自動承認スイッチがオンのときだけ、根拠にした場面の記録文を読み、動作の言葉ごとに再確認して結果を新しい表 `claim_checks`（場面×動作ごとに1行、追加のみ）に書く（`pipeline/claim_scan.py`、ワーカーの `_claim_scan`）。自動承認の claims チェックはこの表を読む。再確認できなかった場面は行が無く、「確かめられていない」と同じ扱い（人の確認待ち）。

| 言葉 | 確かめ方 | モデル | 設定 |
|---|---|---|---|
| 走る・歩く・移動する・位置につく | 追跡の枠の足元の動き。周りの人の動きの中央値をカメラの動きとして引き、体の高さ/秒で見る（`pipeline/motion_check.py`）。周りが3人未満の区間は測らない。測れない場合は「未確認」で、文は人の確認待ちのまま | なし（CPU） | 常にオン（スイッチがオンの作業のみ） |
| シュート・ドリブル・パス・守り | 姿勢の手がかり（腕が頭より上か。エンジンのPythonで測る。測るスクリプトは AGPL-3.0 の ultralytics に依存するため公開版には含めていない）と、場面8枚への2つの再質問（`pipeline/claim_check.py`）。シュートは腕の手がかりが測れて条件を満たすときだけ「確認できた」 | この計算機の中のVLM | `claim_check_enabled`（既定オフ）、`claim_check_vlm_server`（この計算機のみ可）、`claim_check_vlm_model`、`claim_check_max_scenes`、`claim_check_pose_weights` |

高リスクの言葉（シュート・パス・得点）は、再確認が「確認できた」のときだけ通る（以前と同じ）。確認できない・疑わしい場面が1つでもあれば、その文は人の確認待ち。

### 11.2 既定を「オフ」にした理由（測定）

自前の llama-server（Qwen3.5-35B-A3B-VL、Q4、エキスパート24層をCPUに置く設定）で測った。GPU 使用は約13GB（導入後も空き約41GB）、1場面あたり約58秒（2つの質問と姿勢の測定を含む。19本の文・45場面のうち動作の言葉がある36件で2104秒）。通った文が増えない（11.3）のに、モデルサーバーを別に立てる運用と時間がかかるため、既定はオフにした。動きの言葉の確認は軽いのでスイッチがオンの作業では常に行う。使う場合は、モデルサーバーを起動し、`claim_check_enabled: true` と `claim_check_vlm_server` を設定する。再確認の手動実行は `scripts/claim_scan_run.py`（DBのコピー向け）。

### 11.3 公開クリップでの測定

対象はこれまでと同じ公開クリップ（Samsunspor TBF、CC BY 3.0、3分版と60秒版のデモ。生成した文19本）。**同じクリップでの数値で、未知データでの検証ではない。** 車いすバスケ（Splash tv）は、この計算機に公的クリップだけで作った解析結果が無く、エンジンの再実行もできなかったので未測定。

| | 前（0/19） | 再確認の組み込み後 |
|---|---|---|
| 自動承認 | 0 | **0** |
| 人の確認待ち | 19 | 19 |
| 止めたチェック（重複あり） | claims 19、identity 17、evidence 8、confidence 2 | claims 19、identity 17、evidence 8、confidence 2 |

再確認の中身（場面×動作）:

| 動作 | 確認できた | 疑わしい | 否定（映像と合わない） | 測れず |
|---|---|---|---|---|
| シュート | 0 | 3 | 9 | - |
| ドリブル | 2 | 7 | 0 | - |
| パス | 0 | 12 | 0 | - |
| 守り | 0 | 3 | 0 | - |
| 移動（追跡） | 10 | 0 | 0 | 4 |
| 走る（追跡） | 0 | 4（速さが足りない） | 0 | 2 |

claims だけを外すと通るのは1本（run 64）のままで、その文は「守った・パスした」と言う文なので、守り・パスが「確認できた」にならず止まる。つまり、claims を正しく組み込んでも、実データで通る文は増えなかった。主因は identity（19本中17本が「判定不能」。背番号の手がかりが正式には使えないため）と、動作の確認の厳しさ（シュート12件は否定または疑わしい）。

「確認できた」2件（ドリブル）を画像で1件ずつ確認した（公開クリップ由来の画像のみ）:

- cam1-0018-01: 枠の人物が前進しながらボールをつく。正しい。
- cam1-0006-01: 枠が途中で別の人（相手チーム）に移り、枠の人物がドリブルしているとは言えない。**誤通過（枠の人物の取り違え）**。どの文にも使われておらず、この文は identity（判定不能）で止まるため自動承認には至らないが、動作の再確認は人物の取り違えを見ない。人物の確認は identity の担当で、人物が確かめられない限り通らない設計のまま。

自動承認された文が0件のため、「文ごとに画像で正しい／言い過ぎ／誤り」を判定する対象は無い。移動（追跡）の「確認できた」10件は画像を1件ずつは見ていない（どの文も通っていないため）。

### 11.4 結論と次に必要なこと

- 実データで通る文は増えなかった（0件のまま）。無理に通すことはしていない。理由は、(1) 人物が同じ人と確かめられていない（背番号を読む精度が、ゲートを開ける基準に届かない）、(2) 公開クリップでエンジンが書く動作の文自体が合わない（シュートは過去の手採点で15/15が誤り、今回も12件中9件が否定）。
- 自動承認が効くようにするには、背番号の読み取り精度の向上（identity）と、エンジンが書く動作文そのものの精度向上、または動作を書かせない（状態だけを書く）文章の方針が必要。

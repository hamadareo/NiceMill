# トラッキング方式（PFB3x3）の使い方

動画グループごとに、分析の方式を選べます。

- **論文方式（標準）**：これまでどおりの方式です。モデルが、外見と初期位置を手がかりに人物を特定します。
- **トラッキング方式（PFB3x3）**：人物を追跡して P1, P2, … の番号を付け、評価者が番号と参加者を対応づけます。行動の観察は PFB3x3 が行います。貢献の判定・PFB・確認・承認・PDF は論文方式と同じです。

選んだ方式は `submissions.meta["engine"]` に保存されます（`paper` / `pfb3x3`）。値がない古い登録は論文方式として扱います。

## 評価者の操作

1. 「ファイルの登録」で動画の活動を選び、「分析の方式」で「トラッキング方式（PFB3x3）」を選んで、動画グループを登録します。
   - 外見と初期位置は任意です。
   - 「追跡する人数」：空欄のままなら、参加者の表の人数だけを追跡します。活動の間いちばん長く写っているその人数だけに番号を付け、背景の人は追跡しません（`meta["max_people"]`）。別の人数を入れることもできます。0を入れると見つかった全員に番号が付きます（人の多い場面の動画では十数人になることがあります）。
   - 参加者がちょうど4人で、全員の初期位置を「左前・左奥・右前・右奥」のいずれか（重ならないように）で書き、追跡された人物もちょうど4人（追跡する人数は空欄＝参加者の人数）のとき、対応づけに初期値が入ります。
   - 文字起こし（発言者は特定しません）：
     - 文字起こしを貼り付けると、それをカメラ1の音声として PFB3x3 に渡します（カメラ1では自動の文字起こしはしません）。
     - 「文字起こしがなければ、音声から自動で作る」がオンなら、貼り付けのないカメラ（2台目以降、または貼り付けがないときは全カメラ）は、そのカメラの音声から自動で文字起こしします。オフなら、貼り付けのないカメラは映像だけで観察します。
2. 前処理と人物の追跡が終わると、「確認・承認」ページの「人物と参加者の対応づけ」タブに人物一覧の画像が出ます。番号ごとに参加者、または「対象外」（評価しない人・見学者など）を選んで保存し、「参加者特定を確認」を押します。
   - 初期値は自動では確定しません。必ず評価者が確認します。
   - 対応づけのない番号と「対象外」の番号の行動は使いません。どの番号にも対応づけられていない参加者は「根拠不足」になります。
3. 確認すると、行動の観察（PFB3x3）→ 貢献の判定 → PFB の順に進みます。行動の記録は日本語に訳され、番号は「本人」「別の参加者」に置き換わります。確認画面のフレーム画像は、PFB3x3 がモデルに見せた画像です。
4. 対応づけを後から直した場合は、行動の観察以降を再生成するまで承認できません。
5. 行動の記録の翻訳が一部でも失敗すると、「翻訳未完了」と表示され（確認・承認ページと処理状況ページ）、そのままでは承認できません。次のどちらかをしてください。
   - 「行動の観察」をこの段階から再生成する。前回英語のまま残った記録は、保存済みの結果を使わずに1件ずつ訳し直します。
   - 評価者が行動の記録を確かめて保存する（英語の部分は日本語に直せます）。評価者が保存した記録は承認を止めません。英語が残っていれば「英語の記録が残っています」と表示されます。

「処理状況」ページには、人物の追跡と PFB3x3 の各モデルについて、GPU の空きで開始できるかどうかが表示されます。ジョブの表の「処理」列で、どの処理（人物の追跡、PFB3x3（標準）など）のジョブかが分かります。失敗の理由は1行目だけを表示し、エンジンのログのファイル名を添えます（全文はログにあります）。設定にないモデルのジョブは「GPU待ち」になり、理由が表示されます。

## 管理者向け

- エンジンのセットアップ（サーバーで、アプリのフォルダで実行）：

  ```
  scripts/setup_pfb3x3_engine.sh --archive pfb3x3-<commit>.tar <commit>
  ```

  `engines/pfb3x3/` に、PFB3x3 の固定したコミットのコピーと専用の venv が入ります（`ENGINE_COMMIT` にコミットを記録）。YOLO の重みは `data/models/yolo11l.pt` にコピーされます。tarball は Mac で `git -C <engine checkout> archive --format=tar <commit> > pfb3x3-<commit>.tar` で作ります。
- 固定しているエンジン：アプリは、エンジンの特定の版（`ENGINE_COMMIT` に記録）に合わせて作ってあります。アプリは `--tracker` を渡さないので既定の auto になり、既存の別の追跡（TrackID3x3）の完了した実行が同じ動画にあるときだけその追跡を使い、それ以外は標準の追跡です。どちらを使ったかは追跡の実行記録の `tracker` に残り、処理状況の画面に1行で出ます。エンジンのコミットの詳細は、エンジンの公開時に別に記します。
- ライン判定の出力：アプリは、frames.jsonl の `near_court`（選手のコート上の点）と geometry.json の H・誤差（`h_unc_group` など）を読み、選手が線から誤差の幅以内にいるときは「カメラに近い線」とします。詳細は `src/pfb_app/ui/linecall_view.py` のコメントとテストを参照してください。
- 場面の種類（profile）：内容の確認の `scene` は、エンジンに `prompts/check/activity.md` があるときだけ `--activity` を付けて呼びます（PFB3x3 ブランチ profiles-engine の dbb908b。スポーツでない場面に、別の 1 回の依頼（120 秒で打ち切り）で group_task / meeting / presentation / workshop / learning / other を答えます。付けなければ以前と同じ出力です）。いま固定している 58f8341（7bba64a から）にはこのファイルがあるので、スポーツでない場面も自動で選ばれます（20f0a65 までのエンジンでは スポーツ / 一般 だけが自動で選ばれ、ほかの場面はカードで選びます）。行動の観察では、会議・発表・研修・学習活動の作品は、登録の `activity` に場面ごとの英語の一文（見る行動）を足して渡します（エンジンの既存の仕組み）。一般とスポーツは以前と同じです。
- 人物の追跡の速さ：エンジンの `track` は、GPU があれば NVDEC で動画を読み、長辺 1920 に縮めて（枠は元の画素に戻します）、YOLO を fp16・8 フレームずつで動かします。色は `fast`（swscale そのまま）が既定です。ハードウェアの準備に失敗したときは、自動で従来の cv2 の読み込みに戻ります（`raw_meta.json` の `decode` / `fallback_reason` に記録）。環境変数 `PFB_TRACK_DECODE`（auto / nvdec / thread / pipe / cpu）、`PFB_TRACK_HALF`（1 / 0）、`PFB_TRACK_BATCH`（N）で選べ、`PFB_TRACK_DECODE=cpu PFB_TRACK_HALF=0 PFB_TRACK_BATCH=1` が以前の追跡と同じです。追跡し直した作品は、P 番号の付き方が以前と変わることがあります。
- エンジンのモデル：標準 → `qwen3vl-8b`、高精度 → `qwen3vl-32b`。PFB3x3 の vLLM サーバーはポート `pfb3x3_port`（8200）で起動し、GPU の使用量は `pfb3x3_budget_gb`（標準 34 GB、高精度 60 GB）です。開始には「予算 + start_margin_gb」の空きが必要で、空きが `yield_threshold_gb` を下回ると、サーバーを止めてジョブを待ちに戻します。
- 番号から名前：スポーツの登録では、人物の追跡のあとに全員の背番号（車両はゼッケン番号）を GPU で読み取り、自動で選んだ人に「#10」「10号車」の名前をつけます（設定 `number_names`、既定は true）。読み取りの精度の判定（cue_gate）で番号が無効でも読み取りますが、名簿の行の推定に番号を使うのは判定で有効なときだけです。カメラの対応づけに自動で選んだ人が一人もいなければ、そのカメラでは表示名のための読み取りを省きます。false にすると、判定だけで読み取るかどうかが決まります。
- 共有サーバー（標準モデル、`src/pfb_app/worker/shared_server.py`）：常駐ワーカー（`--once` でないとき）は、標準モデルの vLLM サーバーを 1 つだけ自分で持ちます。内容の確認の場面判定、行動の観察と名前の手がかり（`--base-url`）、貢献の判定、フィードバック作成、英語の翻訳を、すべてこの 1 つのサーバーで行います（追跡エンジンの作品の contribution / pfb ジョブは `pfb3x3:standard` で動き、アプリの中に 2 つ目のモデルは読み込みません）。
  - 起動：そのサーバーを使うジョブ（detect、`pfb3x3:standard`）がキューに入ったとき、または決定済みの作品が行動の観察より前（prepare / track など）にあるとき（先行起動）に、裏で 1 回だけ起動します。どちらも「予算 34 GB + start_margin_gb」の空きがあるときだけです。どれかのジョブが GPU 待ちのとき、またはエラーで起動に失敗した後は、先行起動しません。起動中（vLLM がまだメモリを取っていない間）は、ほかの GPU セッションはこのサーバーの予算も足して空きを確かめます。
  - 待ち受け：このマシンの中（127.0.0.1 / ::1）だけで待ち受けていなければ使いません（`ss` で確認し、警告を出して止めます）。その場合、このワーカーでは共有サーバーを使わず、各セッションが以前どおり自分のサーバーを起動します。起動時には `PFB_SERVE_HOST=127.0.0.1` を渡します。固定しているエンジン（58f8341。serve.sh は 20f0a65 と同じ）の serve.sh はこれを受け取って 127.0.0.1 で待ち受けるので、共有サーバーが使われます（8815ccf までの serve.sh は 0.0.0.0 で待ち受けたため、各セッションが自分のサーバーを起動していました）。
  - 保持：そのサーバーを使うジョブがある間と、最後のジョブから 600 秒（`WARM_IDLE_S`）は起動したままにします。ほかのセッションが動いている間も、監視スレッドがこの時間を守ります。
  - 譲る：空きが `yield_threshold_gb` を下回ったら止めます（パスごと、ほかのセッション中も 30 秒ごと）。止めるのは次の場合です。
    - サーバーを使ったセッションが「譲る」「メモリ不足」で終わり、GPU が求められているとき
    - サーバーの異常（応答しない、5xx、プロセスが消えた。ジョブはキューに戻ります）またはセッションの異常終了の後
    - 別のサーバーを使うセッション（高精度）や、モデルをプロセス内に読み込むセッション（標準 / 高精度の紙のエンジン、whisper）の前
    - それを止めれば入るセッションがあって、共有サーバーを待つジョブがないとき
  - 後始末：ワーカーの終了時に、pid を確かめて止めます（最後に必ず stop_server.sh の手順を通します）。強制終了で残った場合は、これまでどおり次のワーカーの起動時に止めます。
  - 並行：貢献の判定とフィードバック作成の依頼は、最大 8 件を同時に送ります（再試行も回ごとにまとめて）。pfb ジョブは最大 8 件を同時に動かします。キューの先頭が pfb のときだけ次の pfb を取り、削除を頼まれた作品のジョブは動かしません。依頼の文面にも、紙のエンジンと同じ JSON スキーマの指示が入ります（翻訳は以前のまま）。
  - 追跡 / names:cpu のセッションは、キューが空になったらすぐ終わります（以前は session_idle_sec 待っていました）。
- 行動の観察の記録：各行動の観察の結果には `provenance`（エンジンのコミット、PFB3x3 の run_meta.json にあるプロンプトのハッシュと settings_sha、翻訳プロンプトのハッシュ、翻訳したかどうかと翻訳モデル、vLLM のバージョンと venv）が入ります。実行の `prompt_hash` は、エンジンのコミット・プロンプトのハッシュ・settings_sha・翻訳プロンプトのハッシュをまとめたハッシュです。
- 制約：PFB3x3 の vLLM サーバーは、エンジンの `configs/models.yaml` が指す venv（既定は `~/extern/venvs/qwen3vl`）で動きます。pfb_app はその venv を読むだけで、書き込みません。この venv が更新されると、エンジンのコミットが同じでも vLLM が変わります（`provenance.vllm_version` で分かります）。将来は、エンジン専用の vLLM の venv を `engines/pfb3x3/` に持つ予定です。
- サーバーの後始末：PFB3x3 の vLLM サーバーの記録は `<data_dir>/pfb3x3_runtime/serve.pid`（と `serve.ident`）です。`scripts/stop.sh` はワーカーとセッションに SIGHUP を送り、セッションはサーバーとエンジンのプロセスを止めてから終わります。強制終了などで残った場合は、次のワーカーの起動時に止めます（pid・ポート・起動時刻が一致するときだけ）。手で止めるとき（アプリのフォルダで）：

  ```
  PFB_RUNTIME_DIR="$PWD/data/pfb3x3_runtime" PFB_SERVE_PORT=8200 bash engines/pfb3x3/scripts/stop_server.sh
  ```

  stop_server.sh も、serve.pid が自分のサーバーを指すときだけ止めます（名前で止めることはありません）。
- 再起動（デプロイ）の前の確認：
  1. 実行中（running）・GPU待ち（waiting_gpu）のジョブがない（`data/app.db` を読み取り専用で確認）。
  2. ポート 8200 で何も待ち受けていない（`ss -Hltn 'sport = :8200'` が空）。
  3. `data/pfb3x3_runtime/serve.pid` がない。
  4. そのうえで `scripts/stop.sh && scripts/start.sh`。`:8501` が 200 を返し、ワーカーが動いていることを確かめます。

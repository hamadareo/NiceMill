# スマホからの大きな動画と 1080p の縮小版

phone-first レーン（2026-10-23）で入れた 2 つの仕組みのメモです。HTTPS は `docs/https.md`。

## 途中から続けて送る（`/pfb-upload`）

Streamlit の送信欄は、ファイル全体をサーバーのメモリに持ち、通信が切れると最初からやり直しです。
4K のスマホ動画（1 分で約 400 MB）には向きません。そこで、画面と同じサーバー・同じアドレスに
小さな送信の窓口を足しました。

- 起動: `streamlit run src/pfb_app/ui/serve.py`（`scripts/start.sh` の既定）。`st.App` が画面
  （`ui/app.py`）と窓口（`ui/upload_api.py`）を同じサーバーで出します。`ui/app.py` を直接起動
  したとき（`PFB_UI_ENTRY=app`）は窓口がなく、画面は Streamlit の送信欄に戻ります。
- 送り方（`ui/wizard/big_upload.py`、ブラウザー側）: 8 MiB ずつ `PATCH`。切れたら待って、サーバーに
  「どこまで届いたか」を聞いて続きから。端末がオフラインになると送信中の要求をすぐ止め、つながると
  再開します。ページを開き直しても、同じファイルを選べば続きから（ブラウザーの localStorage に
  ファイル名・大きさ・日時ごとの送信 ID を保存）。https のときは送信中に画面を消さない（Wake Lock）。
  送信中にページを離れようとすると確認が出ます。
- 守り（`services/chunked_upload.py`）:
  - 合言葉: ページがセッションごとに渡す署名つきトークン（`data/.upload_secret`、0600、HMAC-SHA256、
    24 時間）。2026-10-24 から、合言葉はログインした管理者・評価する人のセッションに結びつき、ログアウトや
    パスワード・役割の変更ですぐ使えなくなります（`docs/accounts.md`）。ヘッダー `X-PFB-Token` で送るので、ほかのサイトのページからは送れません。Origin が
    別のホストなら 403。送信はそれを始めたトークンのものだけで、ほかのトークンからは見えません。
  - 合言葉と送り元は、本文を 1 バイトも読む前に確かめます。作成の JSON は Content-Length が
    4 KiB 以下のものだけ。本文は上限つきで少しずつ読み、1 回分ごとに 120 秒で打ち切ります。
    1 つの合言葉で同時に読む本文は 4 つまで（超えると 429、ブラウザーが待って送り直す）。HEAD は GET と同じ。
  - 大きさ: 動画は `max_upload_mb`（既定 4096 MB）、書類は 200 MB、1 回の要求は 16 MiB まで。
    送り終わっていないものは 1 つの合言葉で 8 つ、全体で 32 まで。
  - 空き容量: 送りかけのものすべての「残り」と新しいファイルを足しても、ops の止める基準
    （`disk_refuse_gb`、既定 15 GB）以上が残るときだけ始めます。作成は 1 つずつ（同時の作成も互いを
    数える）。送るたびにもう一度基準を確かめます（`chunked_upload.ensure_room` は ops の
    `ops.disk.ensure_room` と同じ形で、統合のときに置き換えます）。
  - 持ち主の確認は、送信ごとのロックファイルを作る前に行います（知らない ID ではファイルを作らない）。
  - 置き場所: `data/uploads/.partial/<32桁の16進>.part`。ID 以外の文字はパスに使いません。
    送り終わると `data/uploads/<送信ID>_<名前>` に移り（移す前に記録を書くので、途中で止まっても掃除で見つかる）、「入れて確かめる」で登録されます（登録に
    失敗したら今までどおり消えます）。3 時間進まない途中のファイル（上限と空き容量の計算からも外れる）、48 時間使われなかったファイル、記録のない古い途中のファイルは、
    次に誰かが画面を開いたときに消えます（`sweep`）。
  - ディスクへの書き込みは別スレッドで行い、画面の通信（同じイベントループ）を止めません。
- 残っていること:
  - **ログインがまだないため、tailnet の中でこの画面を開ける人なら、だれでも動画を送れます。**
    トークンは「画面を開けた」印にすぎません。ログイン（監査 #7）が入ったら、トークンをログインの
    セッションに結びつけます。
  - 2 つ目以降のグループの「もう1つ動画を入れましょう」も同じ送信欄です。旧画面（管理用の
    「ファイルの登録」）は Streamlit の送信欄のままです。
  - 同時に送れるのは 1 つの画面から 4 本まで（カメラの上限）。速度は端末の回線しだいです。

## 1080p の縮小版（`services/proxy.py`）

長辺が 2560 を超える動画（4K など）は、登録した直後に裏で 1080p の H.264 版を作ります
（`ionice -c3`・`nice 10`、4 スレッド、1 度に 1 本、PyAV/libx264、音声はそのままコピー、時刻と
画面の向き（縦撮り）はそのまま）。待つ処理はありません。できていれば使い、なければ元の動画を使います。
向きが元と違う縮小版は使いません。縮小版は作業の削除といっしょに消え（ほかの作業が同じ動画を
使っていれば残す）、元のなくなったものは 1 時間に 1 回までの掃除で消えます。

| 段階 | 読むファイル | 理由 |
|---|---|---|
| 中身の確認（detect） | 元の動画 | 8 枚だけ。人の大きさが自動の人選びに効く |
| 準備（5 秒ごとの 854x480 の画像） | 縮小版があれば縮小版（HDR の動画は元） | 同じ小さな画像を 4K からではなく 1080p から作る |
| 文字起こし（論文方式） | 縮小版があれば縮小版 | 音声は元と同じ |
| 人を見つける・名前・したこと・ライン判定（PFB3x3） | 元の動画だけ | P2: 解析部が NVDEC で自分で縮め、枠は元の画素のまま（背番号の切り抜き・ライン判定）。追跡と人のつなぎは小さな画素の違いで変わる（raw IoU .95、P-label 一致 .75）ので、作り直した動画を入れると人の番号が動く |
| 画面での再生 | 縮小版だけ | スマホに 4K を流さない（再生欄は未実装、別作業） |

- HDR（iPhone の HLG）の動画: PyAV の変換は色を SDR に合わせないため、縮小版は OpenCV の
  画像より暗くなります（P2 の「約 25 階調」）。解析は HDR の縮小版を読まず、再生欄もまだないため、
  **いまは HDR の動画には縮小版を作りません**（`SKIP_HDR`、一度見たことだけを記録）。
- 置き場所は `data/proxies/`（受け取り用フォルダには書きません）。元の動画の大きさと更新時刻が
  変わった縮小版は使わず、元が消えたものは次に縮小版を作るときに消します。

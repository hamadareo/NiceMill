# あとから訂正（review_mode = correct_later）

方針：承認の関門をなくし、AI が作った文を承認を待たずに出力する。品質は「あとから訂正できる仕組み」と「訂正の記録」で保つ。AI の文であること・人が確認していない場合があることは、画面と PDF に出し続ける。

## 設計
- 作業ごとの設定 `assignments.review_mode`：`approve`（承認方式。従来のまま）／`correct_later`。列の既定は `approve` で、既存の行は NULL でも `approve` と読む（列の追加だけ）。**画面から作る新しい作業は `correct_later` で始まる**（`services.corrections.NEW_WORK`。`content_check.start_work_from_videos` と `intake.create_assignment_from_form` が渡す。`review_mode=` で変えられる）。前からある作業はそのまま。
- `correct_later` では、人ごとの最新の文（最新の pfb 実行）がそのまま出力対象になる。承認の操作・自動承認は使わない（`services.corrections.approval_enabled` が False）。
- 訂正は新しいテーブル `text_versions` に追記だけする（削除しない）。種類は edit（文の編集）、revert（前の版に戻す）、regenerate（作り直し）、report（「この文は間違い」：人物の取り違え／動作が違う／背番号が違う／その他）、resolve（報告を確認して閉じる）。誰が・いつ・前の文・理由・メモを持つ。edit は新しい pfb 実行も作る（PDF は最新の実行の文を出す）。revert は前の実行の写しを新しい最新の実行にする。
- 版 = edit・revert・regenerate の回数（0 = AI のまま）。

## 確認状況（承認の代わり）
「訂正なし」／「訂正済み 版N」／「誤りの報告あり・確認中」（報告のあとに edit・revert・regenerate・resolve がまだないもの）。

## PDF の表示（正直さ）
- 各人のページの上に「AIが作成した文。人の確認を経ていない場合があります。誤りがあれば訂正できます（訂正の履歴あり）。」と「確認状況：…」。「下書き」「未承認」「承認」「確かめたものです」は出さない。
- ページの末尾に、訂正の記録（版・日時・理由・メモ）、出力日時、文の版（出力のあとに訂正があれば再出力が必要）、訂正の連絡先（`contact=` 引数。なければ団体の設定の「訂正のご連絡先」を「訂正のご連絡先：…」として。それもなければ「訂正のご連絡先：団体の設定で連絡先を入力」）。
- 出典：`credits=` 引数。なければ作業の設定の「出典」（`assignments.credits`、1行に1つ）。それもなく `correct_later` のときは「出典：作業の設定で未入力」。`approve` の作業でも、作業の出典を入れればそれが入る。
- 評価者用 PDF は、表紙と人ごとのページに同じ表示。一覧の札は確認状況。
- 1人1ページ・背番号の呼び方・出典は docs/draft_export.md と同じ（`correct_later` でも使う）。

## 既存方式との関係
- `approve` の作業の PDF・承認・自動承認（docs/autoapprove.md）は変わらない。`correct_later` の作業では承認の経路を使わない（古い承認が残っていても、最新の文を出す）。
- `drafts=True`（下書き）は `approve` の作業で承認前の文を見せる検証用。`correct_later` では帯は確認状況に置き換わり、下書きの帯は出ない。

## 画面（2026-11-23）
- 作業の設定：ステップ1「活動を決める」（既存の作業）の「作業の設定」に、文の出し方（あとから訂正／承認して出す）のラジオと、出典の欄（「出典を保存する」）。どちらもいつでも変えられる。切り替えは `corrections.set_mode`（監査ログ review_mode）。
- 進み具合（`ui/wizard/progress.py`）：`correct_later` の作業は承認を待たない。ステップ5の名前は「文を読む・直す」。文ができると「n人の文ができました。読んで、違っていれば直せます。PDFもすぐ受け取れます」（あなたの番）で、PDF のステップもすぐ開ける。PDF を受け取ると完了。受け取ったあとで、PDF に入っている人の文か確認状況が変わる（新しい pfb 実行、text_versions の行）と、PDF のステップに戻って「…受け取り直してください（再出力が必要）」。PDF に入っている人とは、受け取った PDF に入っていた人（受け取ったときに監査ログ `pdf_downloaded` の `people` に残す）か、いま作る PDF に入る人（`corrections.in_pdf`）。PDF に入っていない人（同一人物の確認が取れていない人など）を直しても出さない。`people` のない前の受け取りでは、前と同じく全員の変化で出す。完了した作業のキャッシュの鍵に text_versions も入れた。解析の待ち画面の最後の行は「文を読む・直す（文ができた人 n / 全 m）」。
- ステップ5「文を読む・直す」（`ui/wizard/step_correct.py`）：一人ずつ、ポスターの流れで ① AIの文を読む（参加者ごとの「よかった所」。確認状況の札、変わっていれば「再出力が必要」の札）→ ② 根拠の場面を見る（文のもとになったコマ。直した文には根拠がないので、直す前の AI の文の場面を出し、そう書く）→ ③ 直せる：「文を直す」（理由とメモは任意。`edit_text`）、「この文は間違い」（理由を選ぶ・メモ。`report_wrong`）、報告があるときは「確認して報告を閉じる」（`resolve_report`）、直前の版が前の文を置きかえたときは「前の版に戻す」（`revert`）、「この人だけ作り直す」（`review.regenerate_from`）。下に「訂正の記録（n件）」（全部の行、前の文と新しい文）。主ボタンは「PDFを受け取る」（フォームを開いている間はその保存・報告）。どの操作も、押したときに見ていた文に対してだけ働く（文が変わっていたら何もしない）。承認・渡す・下書き・未承認の語は出さない。
- 作り直しの記録（`corrections.after_pfb`、ワーカーが pfb のジョブのあとに呼ぶ）：`correct_later` の作業で、前に文があった人の新しい文を regenerate の行にする。前の実行の番号（prev_run_id）を残すので「前の版に戻す」で戻せる。「この人だけ作り直す」（監査ログ regenerate の job_ids にそのジョブがある）なら理由「作り直し」と押した人、ほかの作り直し（解析のやり直し）なら理由「解析のやり直し」。最初の文（版0）は記録しない。
- ステップ6（`step_pdf._live`）：主ボタンは「参加者用のPDFを受け取る」。PDF に入る人と入らない人（理由つき。同一人物の確認を含む）は、出力と同じ `build_report`（写真なし）から出す。同一人物の確認で入らない人がいるときは、背番号の読み取りか「人を確かめる」で確かめていること、「人を確かめる」で確かめると入ること、作業の設定で文の出し方を切りかえられることを書き、「人を確かめると、PDFに入る人が増えます。」と「「人を確かめる」に戻る」ボタンを出す（ステップ5にも、入らない人がいるとき同じものを出す。確認の条件はゆるめない）。受け取ったあとで変わった PDF の人を「再出力が必要」として名前つきで出す。団体の設定（管理者）に「訂正のご連絡先」。
- 同一人物の確認（`export.identity_gate`、docs/identity_gate.md）は動画の作業だけにかける。書類の作業には、取り違える追跡も背番号もないので、かけない（`sheets._sheet`。前は書類の作業でも全員が「背番号が読めておらず…」で PDF に入らなかった）。
- 背番号のない動画（2026-11-23 の2回目）：PDF に載せる条件は「背番号で確認できた」か「人を確かめる段階で評価する人が確認・名前付けした」のどちらか（スポーツでも同じ）。作業の中に確かめる手がかりが1人分もない（背番号がだれにも読めず、人を確かめる段階もしていない）ときは、全員をいつもの表示つきで載せ、ページに確かめていないことを書き、ステップ5の一人ずつの画面に「人を確かめると、取り違えを防げます。」と出す。「人を確かめる」で確かめた人の場面は、承認の作業と同じく全部使う（文が引用した場面の写真も載せる。1場面ずつは確かめず、取り違えは「この文は間違い」で直す）。人が確かめた記録は、画面で直した割り当て（source `teacher`）と、`review.mark_people_checked`（「これで決定して次へ」「参加者の特定を確認」を押したとき、グループの `meta.people_checked` に identity の実行の番号）。

- そのほか：解析の待ち画面の人ごとの札は「文ができました」、人を確かめる画面のやり直しの注意は「文も作り直しになります（前の文は訂正の記録に残ります）」、ホームの「確認待ちの人をまとめて見る」には出さない（代わりに「誤りの報告がある人」、下）、見るだけの人には PDF に入る文と確認状況、ひとことの案内は `*_live` の文、管理用の画面（確認・承認）では承認・取り消し・自動承認を出さず、対象者の状態は確認状況（訂正なし・訂正済み 版N・誤りの報告あり・確認中）で出し、手書きの文は訂正として保存、PDF出力の画面は「PDFに入る文」の数。訂正の記録は、記録があるときだけ出す。
- 一人ずつの ZIP と `handout_parts`（動画を消す前の保存）は、`report.approved` ではなく `report.exported` を使う（`correct_later` で空になっていた不具合を直した）。読み手に合わせた文章は、2回目から `correct_later` の PDF でも使う（下）。言いかえた文は、もとの文が変わると古い扱いになり、PDF は最新の元の文に戻る。

## 承認した文を使っていた機能（2026-11-23 の2回目）
原則：承認した文を使っていた所では、`correct_later` の作業では「誤りの報告あり・確認中」になっていない最新の文を使う（`corrections.usable_run`。SQL では `storage.db._LIVE_OK`）。参加者に届く物には PDF と同じ正直な表示を付ける。
- 成長の記録（`export.growth`、`services.growth`、`growth_view`）：数えるのは使える文のある作業。参加者に届く数は、PDF と同じ同一人物の確認を通った人だけ（`sheets.person_moments`）。つなぐのも使える文のある人だけ（文がない人・報告を確認中の人は「文がまだない人と、誤りの報告を確認中の人は、つなげません。」）。報告を確認中の作業は一覧に残し、「この作業の文は数えていません（文がないか、誤りの報告を確認中か、…）」。成長のまとめのページ（PDF）には、作業ごとに「AIが作成した文・確認状況：…」と、AI の文からまとめたことを書いた末尾の文（`views.GROWTH_FOOTER_LIVE`）。ステップ6に「成長のまとめのページを入れる」。
- 次にためしてみること（`services.tips`）：承認したときに確定したはずの AI の案（`tips.confirm_on_approval` と同じ条件：AI の案・古くない・文が変わっていない・消したあとでない・言い方の注意なし）を、`correct_later` の PDF はそのまま載せる（`auto_ok`、チームは `team_auto_ok`）。その人の文が報告を確認中のときは載せない（チームのヒントは、もとにした人のだれかが報告を確認中なら載せない）。評価する人が確定・削除したものはそれが優先。ステップ5に、PDF に載るかどうかの一行（「AIが作った案です。このままPDFに載ります。…」など）。
- やさしい文章版（`pipeline.plain`、`services.plain_text`、`plain_view`）：もとの文は使える最新の文。参加者用の PDF の言いかえた文には「この文は、版Nの文を、読む人に合わせて言いかえたものです。」。報告を確認中の人は作らない・保存しない（「元の文がないか、誤りの報告を確認中です」）。ステップ6に「参加者用のPDFの文章」。
- 解説動画（`services.explainer`、`explainer_view`、`export.explainer_video`）：使える最新の文があり、PDF に載る人だけ（同一人物の確認を通らない人は「同じ人と確かめられていない（PDFに入っていない）ため、解説動画は作れません。」）。訂正・報告・人を確かめた記録が変わると、前の動画は古い扱い（`person_stamp`）。最後の画面に「この動画は、AIが作成した文章と、そのもとになった場面の記録から作りました。」「人の確認を経ていない場合があります。誤りがあれば訂正できます。」「確認状況：…　文の版：N」。ステップ6から開ける。
- 試合・活動のまとめ（`services.dashboard`）と ききたいことを聞く（`services.ask`）：評価する人の画面なので、同一人物の確認はかけずに全員を出す（承認の作業と同じ）。文は使える最新の文。報告を確認中の人は文を出さず、状態は確認状況（「…の文章は、誤りの報告あり・確認中のため、見せられません。」）。場面の一覧の状態の欄と CSV も確認状況。ステップ6から開ける。
- 見るだけの人（`view_only._live`）：PDF に入る文と確認状況。承認の語は出さない（前の作業から）。
- ホームのまとめて見る画面（`waiting_panel`、`pending_review.reported`）：`correct_later` の作業には承認するものがないので、代わりに「誤りの報告がある人（n人）」：報告の理由・メモ・報告された文と「開く」（その作業の「文を読む・直す」）。まとめての操作はない。
- この解析の確かさ（`quality_stats`、`quality_view`）：`correct_later` の作業の人は、承認の代わりに訂正の記録で数える（文ができた人のうち、訂正なし・文を直した・作り直した・前の版に戻した、誤りの報告を受けた人とうち確認中）。「訂正なし」は誤りがなかった意味ではないと書く。`correct_later` の作業の承認は数えない。「人が承認するまで、文章はだれにも渡りません」の説明は、文の出し方ごとの説明に直した。
- 動画を自動で消す（`services.retention`）：「動画だけ消す」は、`correct_later` の作業では動かさない（人が確かめた文がない作業のため、承認の作業より早く・多く消さない安全な代わりの決まりがない。カードに「あとから訂正の作業のため、動画は自動では消しません」）。「作業ごと消す」は承認の作業と同じ決まり（もともと承認を見ない）に、訂正・報告・報告を閉じたことも「最後の動き」に数える（PDF を受け取ったあとに直すと、受け取り直すまで消えない）ことと、報告を確認中の作業は消さない（カードに「誤りの報告を確認中のため、この作業は自動では消しません」）ことを足した。どちらも、承認の作業より早く・多く消すことはない。

## 残る課題（2026-11-23 の2回目の時点）
- 「動画だけ消す」は `correct_later` の作業では動かない（上）。動かすなら、承認の代わりに何をもって「渡した文が確かめられた」とするか（たとえば PDF を受け取ってから一定の日数、報告がないこと）を決める必要がある。決めるまでは、動画は人が「データの扱い」から消す。
- 手がかりは作業ごとに見る：背番号のない活動でも、だれか1人の番号が読めたり、1つのグループで人が割り当てを決めたりすると、確かめていない人は PDF に入らない（「人を確かめる」で確かめると入る）。グループごとに見るほうがよいかは、使ってみて決める。
- 人が確かめた記録（`meta.people_checked`）は、この版から残す。この版より前に、割り当てを直さずに「これで決定して次へ」を押した作業には記録がない（直して保存した割り当ては source `teacher` なので数える）。
- コートの位置と移動距離は、確認を通った人でも番号の区間に限らずに描く（docs/identity_gate.md）。
- 「人を確かめる」で確かめて新しく PDF に入る人ができても、文や確認状況の行が増えないので「再出力が必要」は出ない（割り当ての変化は数えていない）。
- 試合・活動のまとめ と ききたいことを聞く は、評価する人の画面なので同一人物の確認をかけない（全員を確認状況つきで出す）。参加者にそのまま見せる使い方をするなら、確認をかける必要がある。
- 管理用の画面のページ名「確認・承認」はそのまま（全部の作業で共通のメニュー）。
- 作業の設定のラジオの選択肢「承認して出す」は、`correct_later` の作業でも画面に出る（切り替えのため）。
- ZIP のファイル名は従来のまま。

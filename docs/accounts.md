# 利用する人とログイン（accounts）

2026-10-24 のアカウント機能のメモです（監査の指摘への対応）。組織は 1 つのインストールに 1 つ。
新しい表と、データの根（`assignments`・`growth_people`・`audit_log`）には `org_id` 列があり、今はすべて 1 です。
あとで複数の団体を入れるときに、データの移しかえはいりません。

## 役割

| 役割 | 画面での名前 | できること |
|---|---|---|
| `admin` | 管理者 | すべて。作業の削除、団体の設定、データの扱い、「管理用の画面」、「利用する人」 |
| `evaluator` | 評価する人 | 作業を作る・動画や書類を入れる・人を確かめる・確認して承認・PDF を受け取る・名前を変える・同意の記録・もう一度ためす、成長の記録、試合・練習のまとめ（`/dashboard`）、判定支援、見本 |
| `viewer` | 見るだけの人 | ホーム（「見る」）、作業ごとの承認した文章と、まだのもの、参加者用 PDF の受け取り（受け取り済みの記録はしない）、はじめての方へ、この解析の確かさ、見本（見るだけ） |

- 使えない画面は、その役割のナビゲーションに入れていません（URL を打っても開きません）。
  「試合・練習のまとめ」（`/dashboard?work=<番号>`）も管理者と評価する人だけです。見るだけの人が打つと
  Streamlit の「ページがない」になり、ホーム（その作業の見るだけの画面）が出ます。場面の動画（クリップ）を
  作る前にも、セッションを確かめ直します（取り消されていたら作りません）。
- `ui/pages/` のどのファイルも、最初の行で `access.require_page()` を呼びます（管理用の画面は管理者、
  成長の記録・まとめ・判定支援は評価する人以上、はじめての方へ・見本・この解析の確かさはログインした人）。
  理由: `ui/app.py` の隣に `pages/` があるため、Streamlit は新しく起動したプロセスの最初の実行を古い
  「pages フォルダー」方式で行い（`st.navigation` が一度呼ばれるまで）、そのとき `/users` などの
  アドレスは `ui/app.py`（ゲート）を通らずにページのファイルを直接動かしていました。`ui/serve.py` は
  起動時にこの方式を切り（`access.no_pages_folder_mode()`）、ページ側の確認はそれでも止めます。
- ボタンのコールバックは画面の入口（ゲート）より先に、フラグメントの再実行はゲートなしで動きます。そこで
  役割の確認は毎回、このブラウザーのセッションをデータベースで確かめ直します（`ui/access.py`、1 秒だけ覚える。
  このプロセスで取り消したときはすぐ忘れる）。session_state に残った「人」だけは信じません。
- 画面の中（実行・コールバック・フラグメント）で、有効な管理者・評価する人のセッションがないときのデータベース接続は
  書き込みを拒否します（SQLite の authorizer。書きかえる PRAGMA も拒否）。見るだけの人、ログアウト・取り消し・役割変更・
  期限切れのあとも同じです。画面には「見るだけの人は、この操作はできません。」と出ます。データベース以外に効くコールバック
  （ライブ判定の開始・停止など）は、はじめに `access.refuse_unless_edit()` で確かめます。
- 最後の管理者は、役割を変えたり使えなくしたりできません。

## 最初の起動（デプロイ直後）— 誰も締め出されない手順

誰も登録されていない間は、どの画面を開いても「はじめに、管理者を登録します」だけが出ます（データは見えません）。
登録には一度だけ使える **確認コード** が要ります。

1. サーバーで、アプリと同じ設定（`PFB_CONFIG` を使っているなら同じ値）で:

   ```bash
   cd ~/pfb_app
   env -u VIRTUAL_ENV ~/.local/bin/uv run pfb-admin setup-code
   ```

   `XXXX-XXXX-XXXX` の形のコードが出ます（`data/.setup_code`、0600、24 時間で使えなくなり、このコマンドが新しく作り直します。`uv run pfb-admin create-admin` を
   `--login` なしで実行しても同じものが出ます）。UI のログ（`ui.log`）には「まだ管理者がいない、
   このコマンドを実行する」という 1 行だけが出て、コード自体は出ません。
2. 画面に、コード・名前・ログイン名・パスワード（2 回）を入れて「管理者を登録して始める」。
   その人が管理者になり、そのままログインします。コードのファイルは消えます。
3. ほかの人は「利用する人」（管理用の画面）の「招待コードを作る」で招待します。

画面を使わずに作るとき: `uv run pfb-admin create-admin --login <ログイン名> --name <名前>`
（パスワードは 2 回聞かれます。`--password-stdin` で 1 行読みも可）。これでもセットアップは終わります。
CLI は画面の回数制限を受けません（画面の確認コードが止められていても、サーバーでは作れます）。
画面からの登録は「まだ誰もいない」ことを同じトランザクションの中で確かめます。

「最初に開いた人が管理者」にしなかった理由: `tailscale serve` の後ろではすべての接続が 127.0.0.1 から来るので、
tailnet にいる誰でも先に本番データを取れてしまうからです。

## ログインと締め出しからの戻り方

- パスワード: 10〜128 文字、ログイン名と同じは不可。argon2id（argon2-cffi、MIT。ライブラリの RFC 9106 の既定値）で保存。
- ログイン名: 半角英数と `. _ - @`、3〜32 文字、大文字小文字は区別しない。
- 間違いの制限（各 15 分）: 同じログイン名で 5 回、同じ送り元から 20 回（正しいパスワードでも待ち）。名前があるか
  どうかは言いません。送り元は、アドレス。アドレスがないとき（`tailscale serve` の後ろ、127.0.0.1 への接続）は
  ブラウザーのセッションごとの鍵です。`Tailscale-User-Login` ヘッダーは使いません（設計上の判断。
  サーバーのほかの利用者は 127.0.0.1 に直接つなげ、このヘッダーを好きな値で送れるため）。
  ブラウザーの鍵は、新しいセッションを開けば作り直せます。つまり送り元ごとの制限は回避できるので、
  本当の守りは **ログイン名ごとの制限（5 回 / 15 分）** と **60 ビットのコード**（32 文字から 12 文字）です。
  コードは送り元ごとに 20 回、コードの頭 4 文字ごとに
  10 回（全員で 1 つの枠にはしません）。確認コードは送り元ごとに 10 回、全体で 100 回。いまのパスワードの確かめは本人ごとに 5 回。
  試みは確かめる前に記録するので、同時にいくつ送っても制限を超えません（成功した試みの記録は消します）。
- パスワードを忘れた人: 管理者が「利用する人」→「変える」→「パスワードの再設定コードを作る」（24 時間）。
  本人はログイン画面の「招待コード・再設定コードをお持ちの方」から新しいパスワードを決めます。
- 管理者が全員忘れたとき: サーバーで `uv run pfb-admin reset-password --login <ログイン名>`。
  `uv run pfb-admin users` で一覧。

## セッションとクッキー

- クッキー `pfb_auth_<ポート>`（同じアドレスのほかのアプリと分ける） = `v1.<セッション番号>.<期限>.<ランダム>.<署名>`。署名は HMAC-SHA256、鍵は
  `data/.auth_secret`（0600、初回に作成）。データベースにはランダム部分の SHA-256 だけを残します。
- 期限は 7 日（`session_days`、延長なし）。ページを開くたびにセッションを確かめるので、取り消しはすぐ効きます。
- 取り消し: ログアウト（その端末）、パスワードの変更・再設定（その人の全端末。変えた端末には新しいセッション。
  使われていない再設定コードも取り消し）、役割の変更と「使えなくする」（その人の全端末）。再設定コードは一人に 1 つ
  （新しく作ると古いものは使えなくなります）。
- 全員を終える: `uv run pfb-admin sign-out-all`。

## バックアップを戻すとき

データベースのバックアップ（`scripts/restore.sh`）には、利用する人・役割・パスワードの記録・セッション・招待コードも
入っています。古いバックアップを戻すと、そのあとで消した人、変えたパスワードや役割、取り消したログインが戻ります。
戻したら、すぐに次を行ってください。

1. `uv run pfb-admin sign-out-all`（戻ったセッションをすべて終える）
2. `uv run pfb-admin users` で一覧を確かめ、いまは使わない人を「利用する人」で「使えなくする」
3. 必要なら、パスワードを変えた人に再設定コードを渡す

クッキーの鍵（`data/.auth_secret`）を消すと、すべての端末のログインが無効になります（次の起動で作り直されます）。
- クッキーはサーバーが付けます（`ui/auth_api.py`、`/pfb-upload` と同じサーバー）。ログインのあと、ページには
  60 秒・1 回だけの「引換券」だけが渡り、ページのスクリプトが `POST /pfb-auth/cookie` で引き換えると
  `Set-Cookie: pfb_auth_<ポート>=…; HttpOnly; SameSite=Strict; Path=/`（https・`tailscale serve` では `Secure`）が返ります。
  スクリプトからは読めません。古いクッキーは `POST /pfb-auth/clear` で消します。別のサイトからの要求は 403。
  `ui/app.py` を直接起動したとき（窓口なし）はクッキーを付けず、ログインはページを開いている間だけです。
- **http のままのとき**: クッキーはポートで分かれません（名前にポートを入れているのは、取り違えないため
  だけです）。同じアドレス（同じ IP・ホスト名）のほかのポートで動くほかのアプリにも、ブラウザーは
  このクッキーを送ります。そこを動かす人はログインを横取りできます。直し方は `tailscale serve` による
  HTTPS（`scripts/https_serve.sh`。クッキーに `Secure` が付き、http のアプリには送られません）。
  HTTPS にするかどうかは運用する人が決めることで、この版では設定していません。
- `__Host-` の付いたクッキー名は、`Secure`（https）のときにしか使えないので、いまは使いません
  （http ではポートつきの名前 `pfb_auth_<ポート>` のまま）。HTTPS にするときに、`Secure` のときだけ
  `__Host-pfb_auth_<ポート>` にすること（ほかのアプリからクッキーを上書きされない）を合わせて検討します。
- ASCII 以外の文字を含むクッキー・コード・合言葉は、ただ「無効」として扱います（落ちません）。
- ブラウザーにはエラーの詳細を出しません（`.streamlit/config.toml` の `client.showErrorDetails = "none"`。ログには残ります）。
- 利用者の文字列はすべて `html.escape`（通知の文は markdown のエスケープ）を通しています。
- パスワード・コード・クッキー・鍵は、ログにも `audit_log` にも書きません。

## 操作の記録（audit_log）

`audit_log` に `actor_id` と `actor`（その時のログイン名）を足しました。画面からの操作はすべて、ログインした人の
名前つきで残ります（`ui/common.get_repo` が `Repo.actor` を入れるので、既存の約 30 の記録はそのまま）。
ワーカーの自動の操作は空（システム）です。アカウントの操作も残ります: `login`、`logout`、`login_locked`、
`password_changed`、`password_reset`、`user_created`、`role_changed`、`user_disabled`、`user_enabled`、
`invite_created`、`reset_created`、`invite_cancelled`、`setup_done`。

## スマホからの送信（`/pfb-upload`）

自分の合言葉（`X-PFB-Token`、`data/.upload_secret` の HMAC）の仕組みはそのままにし、ログインに結びつけました。

- 画面は、ログインした管理者・評価する人にだけ合言葉を渡します。合言葉にはその人のセッション番号が入ります
  （`<発行時刻>.<ランダム>.<セッション番号>.<署名>`）。
- 窓口は要求のたびに、そのセッションがまだ有効で、作業を足せる役割かを確かめます。ログアウト・パスワードの変更・
  役割の変更・「使えなくする」で、その端末の送信はすぐ止まります（401「ログインし直してから…」）。
- デプロイ前に渡された合言葉（セッション番号なし）は 401 になります。デプロイをまたいで送信中だったファイルは、
  ページを開き直して選び直してください。

1. いつもの手順でコードを入れ、`uv sync`（argon2-cffi が入ります）。データベースの列は起動時に足され、
   その前にコピー（`app.db.pre-migrate-*`）が作られます。
2. 再起動したら、上の「最初の起動」の 1〜2。確認コードは本人にだけ伝え、Discord などには書かないでください。

## ログインなしで使う（open mode：ログインなしで使えるようにする設定）

設定（`Settings` / `settings.yaml`）の `auth_enabled` を `false` にすると、そのままログインなしで
使えます。

- `ui/auth_ui.py` の `resolve` が「だれでも」（`login: open`、役割は管理者）を返します。ログイン
  画面も管理者の登録画面も一度も出ません。
- サイドバーのアカウントの箱は「ログインなしで使えています。」の一行だけになります。パスワードを
  変えるもログアウトもありません（変えるものがありません）。
- スマホからの送信（`/pfb-upload`）は従来どおり画面自身の合言葉（HMAC）が必須で、合言葉のない
  要求は 401 のままです（open mode で開けるのはこの画面だけ、の枠組みは変わりません）。
  どちらも、直接届いた私的なアドレスの要求だけです（次の「open mode の安全柵」）。
- 操作の記録（`audit_log`）には人 `(0, "open")`「だれでも」が付き、ログインした人の記録と同じ
  形のまま残ります。
- ログインの仕組みそのものはそのまま残ります: `users` / `auth_sessions` / `invites` のテーブル、
  `pfb-admin`、招待コード・再設定コード、`/pfb-auth/*` の窓口。`auth_enabled` を `true` に戻す
  か、設定ファイルなし（既定）で起動し直すと、すぐに元のログイン画面に戻ります。

### open mode の安全柵（rel7 / 2026-11-14）— 公開された入口には出さない

外向きのトンネル（quick tunnel など）が画面のポートにつながったままだと、open mode（全員が管理者）が
インターネットから開けてしまいます。そこで、open mode の「だれでも」は、**私的なアドレスから直接届いた
要求にだけ**出すことにしました（`ui/open_guard.py`、`decide(peer, headers)`）。当てはまらない要求は、
`auth_enabled: true` のときと同じ（ログイン画面。まだ誰も登録されていなければ管理者の登録画面）になり、
`/pfb-upload` は 401 です。設定で外す口は作っていません（外せないことが目的です）。

画面は、ページをつないだ最初のとき（websocket の握手）の送り元と見出しを Streamlit のクライアント情報
から、アップロードは要求ごとに Starlette の要求から読みます。通すのは次の**すべて**を満たすときだけです。

1. 送り元のアドレスが、ループバック（127/8・::1）、私的（10/8・172.16/12・192.168/16・169.254/16・
   fc00::/7・fe80::/10）、Tailscale（100.64/10）のどれか。分からない（取れない）ときは通しません。
   uvicorn は 127.0.0.1 からの `X-Forwarded-For` で送り元を置きかえるため、`tailscale serve`
   経由では tailnet のアドレス（100.x）、quick tunnel 経由では訪問者の公開アドレスになります。
2. 公開プロキシだけが付ける見出しがない: `cf-*`、`cdn-loop`、`true-client-ip`、`via`、`x-envoy-*`、
   `ngrok-*`、`fly-*`、`fastly-*`、`x-amzn-*`、`x-azure-*`、`x-original-forwarded-for` など。
3. プロキシが伝えるアドレス（`X-Forwarded-For` のすべて、`Forwarded: for=`、`X-Real-IP`、`X-Client-IP`）が
   すべて私的。読めないもの（`unknown`、`_hidden`、空）は通しません。
4. ブラウザーが使った名前（`Host`、`X-Forwarded-Host`）が内向き: 私的な IP、`localhost`、ドットのない名前、
   `.ts.net` `.local` `.lan` `.internal` `.home.arpa` `.localdomain` `.intranet`。

`tailscale serve`（`https://myhost.example.ts.net/`）と、tailnet の IP への直接（`http://<server-address>:8501`）は
通ります。確かめ方（実際のサーバーと websocket で確認）: 公開アドレスの `X-Forwarded-For`
と `Cf-Ray` を付けた接続は拒否、`X-Forwarded-For: 100.64.1.2` と `.ts.net` のホストは許可。

**限界（正直に）**: これは要求自身が言っていることで決めます。**このマシンから接続し、見出しを何も付けず、
`Host` も内向きの名前のまま**の転送（`ssh -R`、素の TCP 転送など）は、tailnet の人と同じに見えるので、
この柵では見えません。また、私的なアドレスのプロキシが、見出しを付けずに公開の通信を中継するときも同じです。
つまり柵が閉じるのは、自分が HTTP のプロキシ・CDN・トンネルだと名乗る入口すべて（quick tunnel を含む）で、
素の転送は運用で防ぎます（外向きのトンネルを張らない。`ss -tnp` と `tailscale serve status` /
`tailscale funnel status` を定期的に見る）。拒否したときは、理由の符号だけを 10 分に 1 回ログに出します
（アドレスは出しません）。

ログインなしで使うときは、設定ファイルを `PFB_CONFIG` で指して起動し、そのファイルの
`auth_enabled: false` で切り替えます。デプロイの確認（smoke）は、その設定でホームがログイン画面なく開くこと、合言葉のない
`/pfb-upload` がまだ 401 を返すことを一緒に確かめます。
rel7 の安全柵の確認も同じ smoke に入れます: 公開アドレスの `X-Forwarded-For`（例 `203.0.113.7`）と
`Cf-Ray` を付けた `/pfb-upload`（正しい合言葉つき）が 401 になること、画面は websocket の握手に
同じ見出しを付けるとログイン画面になること（`tests/test_open_guard.py` が同じ規則を固定しています）。
